# 接力文档 2026-09-24：AutoDL 链路系统测试 · 缺陷修复与优化计划

> 状态：**仅计划，未执行**。来源为 2026-09-24 用 agent-browser 对「AutoDL 系统测试」项目（proj_67b93195，dev 前端 5199）做的三条链路系统测试。
> 测试结论先读：三条链路（节点控制台 / REST 直调 / AI 导演对话）全部真实出片，共 4 个视频落在 `storage/videos/vid_1790235*.mp4`、`vid_1790236708*.mp4`。以下为暴露出的问题与可优化项。

## 一、缺陷清单（按优先级）

### P1-1 `prov_e3a19229` 分辨率枚举与 AutoDL 远端实际档位漂移
- **现象**：链路 C 中，规划与用户审批均选择了 `720p竖`，提交被 AutoDL 远端拒绝：
  `AutoDL 提交失败: 参数: resolution 的值: 720p竖 不在 options 列表中`；
  Agent 改用纯文本 `720p` 重试仍被拒；Agent 后续判断为「远端白名单已下线该档位」。
- **证据**：
  - 源声明（`storage/providers/index.json` → `prov_e3a19229.params_schema.properties.resolution.enum`）：
    `["480p竖","480p横","720p竖","720p横","1080p竖","1080p横"]`，与远端实际不符；
  - 实测仅 `480p竖` 出片成功（链路 A）；`720p竖`、`720p` 均被远端拒。
- **影响**：LLM 规划器会按 schema 枚举推荐 720p/1080p 档 → 每次都必然失败，白白消耗审批轮次与用户时间（链路 C 为此烧了 3 次失败 + 多轮审批）。
- **修复方向**（择一或组合）：
  1. **对齐白名单**：将该源 enum 收敛为远端实测真实档位（至少先砍到 `480p竖/480p横`，其余档位确认后再放开）；
  2. **提交前归一**：在该源 python 代码内（`index.json` 的 code 字段）对 resolution 做映射/降级兜底——非法档位自动回落到最近可用档并在返回结果里标注 `degraded_from`；
  3. **源码级档位探测**：给「自定义代码源」增加一个只读「探测远端 options」动作（复用源代码里的 AutoDL 端点拉 workflow detail），把真实档位回写进 params_schema，杜绝再次漂移。
- **验收**：分别用 `480p竖`、`720p竖` 各提交一次 10s 任务：前者成功；后者要么成功要么被**本地校验**提前拦截并给出明确提示（不允许再走到远端 500/提交失败）。

### P1-2 开发端口 `5173` 硬编码散布全客户端（测试期间已临时改了 2 处）
- **现象**：本机 5173 被其他应用占用，dev 前端改跑 5199 后：API/WS/媒体回源全部失效，测试无法进行。
- **证据**：`window.location.port === '5173'` 判断散布在 **15+ 文件**，含：
  - `client/src/services/api.ts`、`client/src/services/agentSocket.ts`（**测试期间已临时改为 `/^51\d\d$/` 正则，未提交，去留待定**）；
  - `client/src/components/canvas/nodes/{VideoNode,TTSNode,ShotCardNode,ProviderNode,MinimalNodes,LoaderNodes,ComfyWorkflowNode,AssetNode}.tsx`；
  - `client/src/components/{timeline/MultiTrackTimeline,export/ExportModal,asset/AssetLibrary,canvas/CanvasResourcePickerModal}.tsx`、`client/src/views/setup/SystemPanel.tsx`、`client/src/components/canvas/CreativeCanvas.tsx`。
- **影响**：任何非 5173 的开发端口下，API/WS/预览图全错；同类逻辑复制了 15 份，后续改一处漏十四处。
- **修复方向**：
  1. 收敛为单一工具模块（如 `client/src/utils/devOrigin.ts`）：统一 `isDev` / `API_ORIGIN` / `resolveMediaUrl()` 三个导出，端口判断改为 `port.startsWith('51')` 或读 `import.meta.env`；
  2. 全量替换 15 处散布定义为引用该模块；
  3. 决定测试期间 2 处临时改动的去留（建议随本项一并收口后保留）。
- **验收**：用 5199（或任意 51xx 端口）起 dev：画布节点视频预览、AI 导演 WS 通道、素材库缩略图三者全部可用；`grep -r "5173" client/src` 无残留业务判断。

### P2-1 AI 导演 `canvas_update_node` 回填键名与节点组件读取口径不一致
- **现象**：链路 C 出片后，Agent 用 `canvas_update_node` 写入 `videoUrl`（驼峰），节点卡片不显示视频（数据已在画布 JSON，UI 不出）。
- **证据**：
  - 新节点 data 实际字段：`videoUrl: /storage/videos/vid_1790236708_5df10ddc.mp4`、`provider: prov_6131876a`、`taskId`；
  - 节点组件读取口径（`MinimalNodes.tsx:399`）：`const vidUrl = d.video_url || d.result_url`；`CreativeCanvas.tsx:240` 的 `OUTPUT_KEYS` 白名单同样是 snake_case（`video_url`）；
  - `server/app/mcp/server.py:2330` `canvas_update_node` 对 patch 原样合并，无键名归一。
- **修复方向**（后端收口为佳）：
  1. `canvas_update_node` 增加别名归一层：`videoUrl→video_url`、`imageUrl→image_url`、`audioUrl→audio_url`、`taskId→task_id` 等（同时兼容两写法落盘）；
  2. 或者在前端 `updateNodeData` 消费侧对已知驼峰键做一次归一；
  3. 顺手在 Agent 工具描述里写明「视频结果键必须用 video_url」。
- **验收**：重放链路 C（或直接手工 PUT 一个驼峰 patch）：节点卡片直接出视频预览，`video_url` 与 `videoUrl` 同时存在且值一致。

### P2-2 节点 Agent 控制台无法关闭，刷新后自动弹出
- **现象**：链路 A 用完后，控制台「×」、Esc、点画布空白、「收起」全部无效；刷新页面后仍自动弹出，持续遮挡画布（测试后期多张截图均被遮挡）。
- **证据**：`NodeAgentConsole.tsx` 的开合状态持久化/恢复逻辑 + 关闭按钮事件（刷新后 selected 节点状态恢复导致重开；关闭路径疑似被运行态判断拦截）。
- **修复方向**：
  1. 排查关闭按钮的 disabled/stopPropagation 链路，保证非 running 态随时可关；
  2. 「刷新后自动弹出」属预期外的持久化——要么不持久化开合态，要么持久化「关闭」态；
  3. Esc 关闭优先级纳入 ctx.registerEscape 统一管理。
- **验收**：打开→关闭→刷新 10 次无一残留；生成运行中点「收起」可以收起（运行态只在后台继续）。

### P3-1 链路 A 规划阶段 LLM 慢/不可用时长时间无反馈
- **现象**：`POST /canvas/agent/generate` 挂 3~5 分钟才返回（LLM 120s 超时 × 多级回退串行），期间控制台只有「Agent 执行中…」转圈，无阶段提示。
- **证据**：`agent_plan.py:265` 的 `llm_service.chat_completion` + `llm_service.py` 的流式→非流式→多 provider 降级链，全部串行 120s 超时。
- **优化方向**：
  1. 规划调用总预算（如 30~45s）+ 快速失败，超时直接走规则规划（规则规划本身已可用，质量足够选源+组参）；
  2. 控制台加阶段文案：「LLM 润色中（最长 30s）→ 降级规则规划」；
  3. 或把 LLM 规划改造成「先规则规划先行提交、LLM 结果异步润色提示词」的两段式。
- **验收**：断掉 LLM Key 重放链路 A：10s 内拿到规则规划结果并开始提交。

### P3-2 素材库悬空记录（文件已删、记录还在）
- **现象**：`GET /assets` 返回 `gen_1788530350_*` 等记录，对应文件在 `storage/generated/` 下不存在；选中即 404。
- **修复方向**：
  1. 启动/访问时对素材做一次存在性懒校验，悬空记录标记为「文件缺失」或直接清理（先备份清单）；
  2. 删除素材时检查是否还有引用（画布节点/分镜）再决定级联。
- **验收**：素材列表全部可预览；不存在返回 404 的条目。

### P3-3 链路 B/C 结果落盘字段口径不统一（顺手项）
- **现象**：`/videos/status` 返回 `video_url`；节点内部轮询兜底 `videoUrl/results[0]/url`（`NodeAgentConsole.tsx:237`、`VideoNode.tsx:59`、`ShotCardNode.tsx:135` 三处各写一遍）；Agent 回填又是驼峰。
- **优化方向**：统一状态协议为 `{status, task_id, video_url, error}` 单一口径，三处前端兜底收敛成一个 `pollVideoTask()` 工具函数。
- **验收**：三处调用点代码合并为一，行为不变。

## 二、非缺陷、值得固化的观察

1. **Agent 自愈链路表现良好，建议固化**：链路 C 的「改写法→test_custom_provider→读源码→shell_exec（被正确拦截）→换源兜底→回填溯源 `fallbackFrom`」完整走通。建议把「换源兜底 + fallbackFrom 溯源」写进导演 Agent 系统提示词的正式准则（当前像是 LLM 自发行为）。
2. **本地引用自动内联 data URI（media_refs）机制验证通过**：本地 `/storage/assets/*.png` 首帧成功送达 AutoDL；20MB 内联上限合理。
3. **审批模式 120s 超时自动拒绝**在工作正常时是好兜底，但叠加 P1-1 类「必失败参数」时会连环弹卡——P1-1 修复后此痛点自然缓解。
4. **测试期间第二次 `/canvas/agent/generate`（非我方触发）也 200 返回**，疑似控制台残留重开时重放——与 P2-2 一并排查。

## 三、建议执行顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| 第 1 批 | P1-1（枚举对齐/归一） + P2-1（键名归一） | 直接影响 AutoDL 链路可用性与产物可见性，改动小收益大 |
| 第 2 批 | P1-2（端口收口为 devOrigin 模块） | 一次性消掉 15 处重复定义，之后开发/测试不再被端口绑架 |
| 第 3 批 | P2-2（控制台开合） + P3-1（规划预算） | 体验类，互不依赖可并行 |
| 第 4 批 | P3-2（素材清理） + P3-3（轮询收敛） | 卫生项 |

## 四、回归测试清单（修复后必跑）
