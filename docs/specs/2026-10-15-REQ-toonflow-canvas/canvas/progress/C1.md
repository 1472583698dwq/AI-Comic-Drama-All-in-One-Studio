## 1. 舞台在 CSS 缩放容器里拾取不准

- **原因**：`stageCore` 的 `frameClientRect()` 把 `getBoundingClientRect()`（屏幕像素，含 React Flow 的 `scale(zoom)`）和帧区域（letterbox，布局像素）直接相加。画布缩放 ≠ 1 时，关节拾取的 NDC 偏了。
- **修法**：`picking.ts` 新增纯函数 `layoutRectToClient(rect, layout, sub)`：按「屏幕 rect 尺寸 / 布局尺寸」的比例，把元素内的布局区域换算到屏幕坐标。`stageCore` 用它算帧区域的屏幕矩形，然后交给 `raycasterAt`。量的是画布元素本身；量不到（未布局、jsdom）就退回容器。
- **3D 片场页**（`Director3DStage.tsx`）没有改：它传给 `raycasterAt` 的是整个容器的 `getBoundingClientRect()`，没有混入布局像素，任何缩放下本来就对。`raycasterAt` 的行为没变，只是把参数类型命名为 `ClientRectLike`，并在注释里写明 rect 必须是屏幕像素。
- **测试**：
  - `picking.test` +2：换算公式（缩小 0.5、放大 2、不缩放、量不到尺寸）；缩放 0.6 / 1 / 2 下拾取到同一个关节。
  - `stageCore.test` +1：容器缩放 0.6 / 2，且 16:9 画幅放在 640×480 容器里（上下留边），按屏幕坐标拾取右肘。这条在旧逻辑下会失败，已验证。

## 2. `recordCameraPath` 尾部丢帧

先用无头 Chromium 149 做了实测，确认原因：
- MediaRecorder 用「画面被采集的时刻」当帧时间戳。WebGL 读回像素（SwiftShader 下）和编码在别的线程排队，机器忙时会落后 0.5～2s。
- 旧逻辑在末帧后只等 66ms 就 `stop()`，队列里还没进录制器的帧被直接丢掉。
- Chrome 的 MP4 封装要等到 `stop` 才一次性输出（36B 头 + 整段 moov/mdat），所以 MP4 没法用 `requestData` 看进度。WebM 是边录边吐数据的。
- 末帧之后如果不再画，画面不变就不会产生新帧，成片不会因为多等而变长。实测末帧后多等 0.3～2s，时长不变。

**修法**（API 不变，只改 `stageCore.recordCameraPath` 内部）：
1. **出帧对齐网格**：帧按 1/fps 的网格出。运镜内容 [0, duration] 均匀映射到墙钟 [0, duration − 1 帧]，所以末帧（终点机位）的时间戳是 duration − 1 帧，成片时长 = 末帧时间戳 + 一帧 = duration。首帧是起点机位，末帧是终点机位。
2. **末帧后不再画新帧，等管线排空再停录**：
   - Chromium：在克隆的视频轨道上挂 `MediaStreamTrackProcessor` 当探针，看到末帧的时间戳出了采集管线后，再留 200ms 给编码器，然后 `stop()`。
     - 时间戳原点：Chromium 画布采集的时间戳从建流时刻（0）起算。机器忙时探针会漏掉开头几帧，所以只要第一帧时间戳落在 [0, 到达时刻] 内，就认定原点是建流时刻。
     - 兜底：末帧之后有帧到达，且之后 1s 没有新帧，也算排空。
   - 没有探针的浏览器：录制器还在吐数据（WebM、分片 MP4）就继续等，直到连续两次 `requestData` 都没有新数据，至少等 0.6s；录制器不边录边吐数据时，盲等 1.5s。
   - 总等待上限是 4s + 运镜时长，封顶 15s；管线卡死时尽力而为。取消（signal）会立即停。
3. **测试**：`stageCore.test` +1。用假的 MediaStreamTrackProcessor 模拟采集管线落后 350ms，断言以下几点：
   - 首帧是起点机位，末帧是终点机位；
   - 末帧落在 duration − 1 帧；
   - `stop()` 发生在末帧送达之后；
   - 末帧之后没有再画新帧。

   原来的「无 MediaRecorder 报错 / 有就产出 Blob」用例还在，现在走的是无探针分支。

**实测**：无头 Chromium 1228，舞台 1280×720，运镜 2.5s。

| 条件 | 旧逻辑成片 | 现在成片 | 录制总耗时 |
|---|---|---|---|
| 真 GPU | 2.54～2.55s | 2.503～2.508s | 2.7s |
| SwiftShader | 2.29～2.55s（随机截尾） | 2.498～2.507s ×4 | 3.3～3.4s |

## 3. 素材库把非白名单扩展名存成 `.png`

- **修法**（`asset/manager.py`）：
  - `resolve_asset_ext(filename, content_type, head)`：先看文件名扩展名，再看上传的 content-type（去掉参数），再看文件头，最后才按旧规则落成 `.png`。
  - 白名单 `ASSET_FILE_EXTS`：
    - 图片 png/jpg/jpeg/webp/gif/bmp/avif；
    - 视频 mp4/m4v/mov/webm/mkv/avi/ogv；
    - 音频 mp3/wav/m4a/aac/ogg/oga/opus/flac/weba；
    - 3D glb/fbx。
  - html / svg / js 这类同源可执行内容和未知格式仍落成 `.png`，不按原类型对外提供。扩展名统一转小写。
  - 文件头能认出 PNG / JPEG / GIF / WEBP / WAV / AVI、ftyp 系列（mp4 / m4a / mov / avif / m4v）、EBML（webm / mkv）、OGG、FLAC、MP3（ID3 / 帧同步）、ADTS AAC、glTF、FBX。
- **content-type**：`register_asset_content_types()` 在模块导入时把每个保留扩展名的标准类型登记进 `mimetypes`。`/storage` 静态服务（Starlette `guess_type`）因此统一回标准类型：
  - m4a → `audio/mp4`（macOS 系统表原来给 `audio/mp4a-latm`）；
  - glb → `model/gltf-binary`（原来没有登记，回的是 `text/plain`）；
  - flac / aac / wav / weba 同样换成标准类型。
- **路由**（`asset_routes.py`）：单个上传、批量上传、PUT 换文件三处都把 `UploadFile.content_type` 传下去。文件名是 `blob` / 不带扩展名时，按 content-type 保留真实格式。
- **顺手**：复制素材（`duplicate_asset`）时优先复制 `file_url` 指向的那个 `original.*`。换过不同扩展名的文件后，目录里可能同时有多个 `original.*`。
- **测试**：`server/tests/test_asset_file_ext.py`，64 条，storage 指到临时目录，云端同步队列打桩。覆盖：
  - 按文件名 22 种、按 content-type 12 种、按文件头 15 种解析；
  - 文件名优先；危险 / 未知类型回落 `.png`；
  - 每个保留扩展名都登记了 content-type；
  - `POST /assets` 上传 10 种格式：落盘扩展名、`file_url`、字节一致，`/storage` 回的 content-type 正确；
  - 无扩展名文件按 content-type / 文件头判断；
  - 批量上传；
  - PUT 把 png 换成 webm 后再复制。
