## 1. 目标与边界

**要做**：把前端可插拔 UI 区域统一登记进一个注册表，由现有开关体系驱动；开关切换后界面立即变化（不刷新、不重启）；提供不可关闭的最小形态兜底。

**不做**：
- ❌ 不新增后端契约（不开 `/ui-registry` 之类的端点）；
- ❌ 不改开关语义（三层真相源保持不变）；
- ❌ 不推倒重来（绞杀者模式，逐期迁移）；
- ❌ 一期不做代码级热替换（不引入 Module Federation / 动态下代码）。

**明确的口径**（用户确认）：
1. 热插拔 ≠ 所有 UI 都可插拔。必须有**最小形态**，其开关不可关闭，否则会出现「关掉自己后无法再打开开关」的死锁。
2. 每期收尾都要给出可复核的验证方式与文档记录。

## 2. 现状盘点（改造前的事实）

### 2.1 已有四套机制

| 机制 | 真相源 | 写入方式 | 前端落点 | 当前覆盖 |
|---|---|---|---|---|
| 页面开关 | 后端 `GET /api/v1/pages` | `POST /api/v1/extensions/page:<id>/enable\|disable` | `stores/usePageStore.ts` → `App.tsx` `PAGE_HOSTS` | 页签准入、入口可见性；关掉后后端对应接口族 404 |
| 功能开关 | 后端 `GET /api/v1/features` | 后端 features 接口 | `stores/useFeatureStore.ts` → `views/setup/FeaturesPanel.tsx` | 页内进阶能力 |
| UI 开关 | **localStorage** `ai_manju_ui_switches` | 本机即时写 | `stores/useUiPrefsStore.ts` | 纯呈现偏好（如侧栏快捷区） |
| 插件贡献 | 后端 `storage/extensions/state.json` + 插件目录 3s mtime 热重载 | `POST /extensions/{id}/enable\|disable` | 声明式 DSL 由各宿主渲染（`storyboard/slots/`、`canvas/nodes/ExtNode.tsx`、`ExportModal`、`Director3DStage`、主题同步） | 13 类扩展点，**仅声明式，不能注入 React 组件** |

### 2.2 现有缺口（本方案要解决的）

1. **硬编码面过大**：`App.tsx` 里 11 个 host 的映射表（`PAGE_HOSTS`）之外，还有 10 个全局弹窗/覆盖层硬编码在 `App.tsx` 的 JSX 里（`ScriptImportView`、`ExportModal`、`McpToolsModal`、`SkillStudioModal`、`ProviderManagerModal`、`ProviderCreateModal`、`WorkflowImportModal`、`WorkflowInspectorModal`、`GlobalDialogContainer`、`FirstRunWizard`），以及 `Header` / `Sidebar` 的入口按钮、`AgentChatDrawer` 的显示条件、`ContextTipCard` 的页内条件——这些都不在开关体系里。
2. **没有统一挂载点抽象**：每加一个 UI 区域，都要改宿主 JSX；插件想贡献 UI 只能走声明式 DSL，内置能力与插件走上完全不同的两条渲染管线。
3. **插件启停的 UI 侧无推送**：后端 enable/disable 后，前端要靠用户切页/刷新才发现变化。
4. **缺「最小形态」概念**：目前只有 `config` 页在契约里标了 `locked`，没有推广到其他必须常驻的 UI 区域。

### 2.3 已有能力与插件的分类盘点（决定开关分几类）

> 结论先行：**开关分 4 类**（`page` / `feature` / `prefs` / 插件启停），不再新增第 5 类。插件贡献不自带独立开关层——它**继承宿主所在层的开关**，再与「插件自身启用态」做与运算。
>
> **有效可见性公式**：`可见 = 插件启用 ∧ 宿主页开关(page) ∧ 功能闸门(feature) ∧ 呈现偏好(prefs)`（不含的层视为恒真；`locked` 条目短路全部）。

#### 2.3.2 大功能页的「页开关 vs 功能开关」切分（分类复杂点）

画布、分镜台这类大功能页**同时是 page 和若干 feature 的容器**，切分原则：

- **page 层只管「整页进不进 + 整族接口 404」**——一刀切，不细分页内区域；
- **feature 层管「页关不掉、但能力想单独关」的进阶能力**（沿用后端 `features.py` 既有定位）；
- **prefs 层只管「开着但不想看见」的呈现**。

| 大功能页 | 页开关（已有） | 页内 feature 拆分（**2026-10-10 定稿**） | 说明 |
|---|---|---|---|
| 创意画布 `canvas` | `page: canvas`（关掉后 `/canvas` `/custom-nodes` `/canvas-nodes` 404） | ① 自定义代码节点执行（`custom_nodes` 沙箱，安全敏感）→ **保留 feature `canvas_custom_nodes`，默认关**；② 画布时间线节点 → **不升 feature** | ② 与多轨剪辑页**共用 `/api/v1/timeline`**：后端已用 `require_any(["canvas","timeline"])` 处理——关掉画布不杀剪辑页；前端注册表对应条目要按「任一宿主页开即渲染」处理，不能简单绑单一 page id（不升 feature 也沿用此口径） |
| 分镜台 `studio` | `page: studio`（`/storyboard/slots` + `/onekey` 404） | ① 插件分镜槽位（`storyboard_slots` DSL 槽）② 一键成片入口 → **均不升 feature** | `/onekey` 与成片工作室页**共用**：同属跨页能力族，处理同上；两个入口都由「页面开关 + 插件启停」表达，不另设 feature |
| 成片工作室 `onekey` | `page: onekey` | 导演组选择器（受 `feature: agent_teams` 二次闸）→ **不新增 feature** | 已是「page ∧ feature」叠加的现成样本；`agent_teams` **保持默认关**（可选进阶） |
| AI 导演 `agent` | `page: agent` | 已有：`agent_multimodal`、`agent_subagent`、`agent_teams` → **前两条改默认开，`agent_teams` 保持默认关** | 本页是 feature 层发源地；前两条是「开箱完整链路」必需（看图 / 产物回投 + 子代理集群） |
| 3D 片场 `director3d` | `page: director3d` | 导演包贡献（`director_packs`，现仅靠插件启停） | 无需新增 feature，插件启停已够 |

**页内 feature 定稿口径（2026-10-10，用户确认）**

目标：**新实例开箱即可走通一条完整的视频制作链路**（创意画布 / AI 导演 → 分镜台 / 成片工作室 → 多轨剪辑 → 导出），不需要用户先去翻一遍开关。口径分四层，各管各的：

1. **页面层（page）不动**：11 页已全部 `default: True`（`core/pages.py`），`config` 仍 `locked`。画布 / AI 导演 / 设置本来就是开箱即用，不存在「默认打开」的待办。
2. **功能层（feature）由「出厂全关」升级为「显式白名单」**：
   - 默认**开**：`agent_multimodal`（多模态附件与看图）、`agent_subagent`（子代理委派）—— 理由：一键成片依赖子代理集群、视频链路要看参考图与产物回投，这两条属**链路必需**；
   - 默认**关**：`canvas_custom_nodes`（画布自定义代码节点，会执行用户代码，安全敏感）、`agent_teams`（导演组，可选进阶）—— 用户需要时自行在 设置 → 功能开关 打开；
   - **零新增 feature id**：上表其余候选（画布时间线节点、`studio` 分镜槽位 / 一键成片入口、`director3d` 导演包贡献、设置台的注册表视图 / 诊断面板）一律不升 feature，仍由页面开关 + 插件启停 + `prefs` 层表达。
3. **生成源（provider）不进开关体系，也不做内置兜底**：开箱**不预置**任何可用生成源（含 Mock），需要用户在 设置 里**自行配置**（云端密钥或本地服务）。未配置时链路的「生成」环节不可用，界面要给明确引导（去配置生成源），而不是静默失败 —— 即「开箱完整链路」以「用户已配置至少一个源」为前提。
4. **最小形态（锁定层）不变**：锁定条目本来就永久渲染，不参与「默认开 / 关」的讨论（见 §5）。

**判断一条能力要不要升 feature 的三条判据**（替代此前的「提案，Phase 3 定稿」）：

1. 它**混在页面里、关页面关不掉**（这是 feature 层存在的唯一理由）；
2. 关掉后是**整块能力消失、但仍自洽**的降级（不是「少个按钮」）；
3. 它**既不是开箱核心能力**，**也不是插件贡献**（前者应直接可用，后者由插件启停解决）。

三条同时成立才升 feature；上表候选全部落在第 2 / 3 条上，故不升。

**落地前提（代码侧，待执行）**：

- `core/features.py` 把 `agent_multimodal` / `agent_subagent` 的 `default` 改为 `True`；
- `tests/test_features.py::TestDefaults` 由「全部 `default is False`」升级为**白名单制**（默认开的 id 必须出现在显式常量内，其余必须 `False`，分组断言保留）—— 原契约不放宽为「谁都可以默认开」；
- **不回溯**：`features` 只在文件缺失时回落 `default`（见 `features.py` 顶部设计说明），故新默认只影响**新装 / 未写过 `storage/features.json`** 的实例；老实例保持用户当前设置，不写迁移、不动其文件。

#### 2.3.3 由此确定的 4 类开关（最终分类）

| 类别 | 真相源 | 管什么 | 现有实例 | 锁定规则 |
|---|---|---|---|---|
| **页面开关** `page` | 后端扩展覆盖层（`page:<id>` 进出 `state.json`） | 整页准入 + 入口可见性 + 接口 404 | `PAGE_DEFS` 11 页（`config` 后端已锁） | `config` 不可关 |
| **功能开关** `feature` | 后端 `storage/features.json`（**显式白名单默认值**，见 §2.3.2 定稿口径） | 页内进阶能力、跨页能力族的能力闸 | `agent_multimodal`（默认开）/ `agent_subagent`（默认开）/ `agent_teams`（默认关）/ `canvas_custom_nodes`（默认关） | 开关面板自身所在 UI 不可关（见 §5） |
| **UI 偏好** `prefs` | 本机 localStorage | 纯呈现显隐，不碰后端 | `sidebar_chat_history` | 无（全关也不影响自救路径） |
| **插件启停** `plugin` | 后端 `storage/extensions/state.json` + 目录 mtime 热重载 | 一个插件的**全部贡献**整体上下线（按 `source` 精确回滚） | `example-drama-pack` | 插件中心入口所在页（`config`）不可关 |

**不设第 5 类「扩展点级开关」**的理由：13 类扩展点的宿主归属已能被上表 4 类完全表达（2.3.1 每行的「生效前提」都是这 4 类的与运算）；再细分会产生「插件开了但某扩展点单独关」的碎片化状态，与后端「精确回滚、不留孤儿」的生命周期语义冲突。若未来确有需求，优先把该能力提为 `feature`（如 2.3.2 的候选拆分），而不是新开一层。

### 2.4 开关与样式替换的边界

> 背景：把所有前端区域收进开关管理后，需要明确「开关」与「样式 / 实现替换」的边界，避免把版本选择错误地塞进开关层。

1. **开关只管存在性，不管形态**：`resolveEnabled(entry)` 只决定渲不渲染；样式、布局、组件实现全在 `render` 内部，开关层不感知。同理，page / prefs 的区分维度**不是 UI 面积**，而是关掉的后果——判定口诀：**关掉后后端能力要不要跟着关？要 → `page` / `feature`；不要 → `prefs`**（侧栏快捷区一大块 UI 是 `prefs`，导演组选择器一小块是 `feature`，面积与层级无关）。
2. **页面换样式的正路 = 在已注册版本中选择**：
   - **换实现**：同 id 重复注册 = 替换 `render`——开关状态原样保留、无中间态闪烁、无页面内 state 丢失（热重载与 React 严格模式本来就依赖这条语义）；
   - **换肤**：走主题 Token（`themes` 扩展点只允许覆盖已登记 CSS 变量，见 §9.1）；
   - **多版本并存选择**：`variant` 机制（Q7 定稿引入），见 §2.4.1。
3. **禁止把样式替换建模成两个开关**（旧版一个、新版一个）：开关体系没有互斥概念，会出现「两个都开」的非法组合；且切换 = 先卸载再挂载，产生中间态闪烁 + 页面内 state 丢失。
4. **`locked` 与实现正交**：locked 锁的是「存在性」，不是「版本」——locked 页面照样可以换样式。
5. **两类「换皮」真相源不同，不得混用**：`prefs` 落 localStorage（各机器各自独立）；`themes` 是后端状态（跨机器一致、受插件启停管理）。看起来都是换皮肤，前者不进后端契约，后者属第 4 类开关——不能为了统一而把主题塞进 prefs。

#### 2.4.1 页面版本切换机制（定稿）

四类开关之下「切换页面前端版本」**不新增第 5 类开关，也不改 page 开关**：

1. **不集成进 page 开关**：page 开关是后端布尔契约（整页准入 + 接口族 404），往里加「开哪个版本」选项等于改开关语义，违反 §1 边界。
2. **不需要新注册表**：UIRegistry 本身就是版本容器——同一页的多个版本 = 同 host 下、带 `variant` 标识的多条页面条目（如 `page.studio@classic`、`page.studio@v2`，契约见 §3.1）。
3. **激活版本 = prefs 层单选偏好**：`page_variant.<pageId>`（字符串值，非布尔），落 localStorage、各机器独立；缺省回落 `default` 变体。UI prefs store 需从纯布尔扩出一类单选字符串偏好（Phase 3）。
4. **渲染规则**：`resolveEnabled` 对带 `variant` 的条目额外校验「激活版本匹配」；同一 host 的多版本条目**至多渲染一条**（天然互斥，不会双版本同屏）。
5. **归层判定照 §2.4 口诀**：两版**后端能力等价**（纯样式 / 布局差异）才允许作为 variant 并存；能力不同就不是版本问题——要么拆 `feature`，要么同 id 替换实现。
6. **兜底**：激活的 variant 条目不存在（如插件提供的版本被停用）→ 自动回落 `default` 变体并 toast 提示，不落空白。
7. **切换代价**：一次卸载 + 挂载，页面内 state 丢失（与切换页面等同），声明为已知语义，不做状态迁移。

## 3. 核心设计：统一 UIRegistry

### 3.1 条目契约

```ts
interface UIEntry {
  id: string;            // 全局唯一，如 'modal.provider-manager'
  kind: 'page' | 'panel' | 'modal' | 'toolbar' | 'sidebar-block' | 'prefs';  // 展示分类，不参与判定
  host: string;          // 挂载点：'app' | 'page' | 'sidebar' | '<page>.toolbar' ...
  order: number;         // 同挂载点内排序（沿用现有 order 约定：数字小的在前）
  locked?: boolean;      // 最小形态：跳过一切开关判断，永远渲染
  variant?: string;      // 页面版本标识（同 host 多版本并存用；激活版本由 prefs 单选偏好决定，见 §2.4.1）
  scope?: 'page' | 'feature' | 'prefs';  // 开关归属层
  switchId?: string;     // 对应开关 id；缺省 = 迁移期常驻（未绑定开关）
  source?: 'builtin' | `plugin:${string}`;  // 来源，供按源批量回滚
  layout?: React.ComponentType<{ children: React.ReactNode }>;
                         // 页面条目的布局声明（见 §9.2「STAGE_HOSTS」）：只有页面槽会用它包住 render
  render: React.ComponentType<any>;
}
```

> **`kind` 的口径（2026-10-09 追认，未完成清单第 8 条）**：`kind` **只作展示分类，不参与任何判定**
> —— 判定只看 `locked` / `scope` / `switchId`。取值按**结构**归类：页面槽 `page`、覆盖层弹窗 `modal`、
> 壳（顶栏与横幅）`toolbar`、侧栏块 `sidebar-block`、设置台面板 `panel`；`prefs` 为**保留取值**
> （当前无使用者）：仅当「prefs 层且无法用上述任一结构性取值归类」时才用 —— 层归属一律由
> `scope: 'prefs'` 表达，不用 `kind` 重复表达。落地见 `client/src/ui-registry/types.ts`。

### 3.2 运行时三条规则

1. **注册**：内置功能在模块顶层静态注册；插件贡献在启用时动态追加、停用时按 `source` 精确移除（与后端「精确回滚」对称）。同 id 重复注册 = 替换而非追加（兼容热重载与 React 严格模式双调用）。`register()` 返回反注册函数。
2. **查询**：`useUIEntries(host)` 返回该挂载点下、按 `order` 排序、且 `resolveEnabled(entry) === true` 的组件列表；宿主只写 `entries.map((e) => <e.render key={e.id} />)`。
3. **生效**：`resolveEnabled` 内部读 `usePageStore` / `useFeatureStore` / `useUiPrefsStore`（zustand 订阅）。开关一变，所有订阅宿主自动重渲染——**这就是「热」的来源**，不刷新、不重启。

### 3.3 开关真相（不新造）

| `scope` | 判断来源 | 关闭后的效果 |
|---|---|---|
| `page` | `usePageStore.values[id]`（开关 id = page id） | 页签不可进入 + 入口隐藏（后端同时 404 能力） |
| `feature` | `useFeatureStore.values[id]` | 仅该区域隐藏，其他页内能力不受影响 |
| `prefs` | `useUiPrefsStore.values[id]`（本机 localStorage） | 纯呈现变化，不影响后端 |
| 插件条目 | `/extensions` 返回的启用态 + 覆盖层 | 条目从注册表移除 |

补充分支与默认值：
- `locked: true` → 短路，无视以上全部；
- `switchId` 不存在（迁移期过渡态）→ 常驻，但已进注册表，后续绑定开关零成本；
- 开关 store 未加载完（`loaded === false`）→ 宿主渲染加载占位，避免「默认全隐藏再逐个蹦出」的闪烁（沿用 `App.tsx` 现有 `pagesLoaded` 做法）。

### 3.4 最小形态（锁定层）

**判定原则**：一个 UI 区域若被关闭会导致「开关本身不可控」或「应用不可用」，即必须 `locked`。
具体清单见第 5 节（在真实代码盘点后确定）。

- 风险最低：该层开关订阅已存在，改造只是「映射表 → 注册表」。

## 5. 最小形态清单（代码盘点结论）

盘点范围：`client/src/App.tsx`、`components/navbar/{Header,Sidebar}.tsx`、`views/setup/SetupView.tsx`、`components/ui/NoPageEnabled.tsx`、`stores/useUiPrefsStore.ts`，以及后端 `server/app/core/pages.py`（`is_locked`）与 `core/features.py`。

### 5.1 判定原则（复用后端既有口径）

一个 UI 区域必须 `locked`，当且仅当它满足以下任一条：

- **A. 自救必需**：关掉后用户无法再把其他开关打开（「关掉开关面板」类死锁）；
- **B. 应用壳必需**：关掉后剩余 UI 无法正常承载内容（容器、边界、反馈通道）；
- **C. 契约已锁**：后端已把它标为不可停用（目前只有 `config`，见 `pages.is_locked` / `test_pages.py::TestLockedConfig`）。

### 5.4 由盘点推出的三条设计约束

1. **locked 只是前端渲染语义，不改后端契约**：把 `Header` / `Sidebar` 壳 标 `locked` 是纯前端行为，不加任何后端字段（符合「不新增后端契约」）。唯一的后端锁定事实仍是 `config`，两者方向一致、不冲突。
2. **`locked` 条目禁止绑定 `switchId`**：注册表在 `register()` 时校验，避免出现「标了 locked 又绑开关」的自相矛盾条目（要么永远显示，要么可关，不允许既 locked 又可关）。
3. **设置页自身不可写 `locked` 的子页签**：`SetupView` 的 5 个一级页签（`core/output/features/extensions/system`）中，`features` 必须常驻；其余页签可按 `prefs` 开关控制，但**不得出现「5 个页签全关」**——这与「页面开关全关仍能进设置」是同一类保护。

## 6. 错误隔离、失败语义与回滚

1. **逐条错误边界**：`UISlot` 渲染每条时包一层轻量 `ErrorBoundary`（复用 `components/ui/ErrorBoundary`，`name` 用条目 id）。单条崩溃只替换该条为不打扰的占位块，宿主与其他条目不受影响。
2. **不自动关闭开关**：崩溃不静默改用户状态；开关本身就是手动杀开关。
3. **注册幂等**：同 id 重复注册 = 替换。
4. **按源回滚**：插件 disable/uninstall 按 `source` 批量反注册；reload = 先清旧、再追加，不留孤儿条目。
5. **加载期不闪**：`loaded === false` 时渲染占位；`locked` 条目任何时候都渲染。
6. **无僵尸态**：开关关闭 → 宿主卸载条目 → 弹窗自然消失；打开状态仍由既有触发器管理作为唯一来源。

## 12. 扩展点桥接草案（Phase 5 提案，**待确认**）

> 背景：未完成清单第 3 / 4 / 9 / 10 条（导出器 / 导演包 / 画布调色板 / 页内面板收敛进注册表）卡在同一个问题上 ——
> 这些渲染都需要**宿主回调**（`ExportModal` 的「运行导出」、画布的 `createNode`、3D 片场的装配、槽渲染要 `ctx`），
> 硬塞进注册表会破坏「注册表只管存在性」的口径。**M3**（标注对 `app` / `main.tips` 失效）同源：
> 这类脱离文档流的宿主不该被槽包一层，应由条目**自己标**。
>
> 第 2 条（工具动作条目化）已经给出了这条桥接的**最小可用形态**（`ToolbarChromeContext` + 条目自标），本节把它定成可推广的约定。

### 12.1 三条规则（提案）

1. **声明进注册表，回调由宿主注入**：条目仍是 `UIEntry`（`id / kind / host / order / scope / switchId / source / render / meta`），
   但 `render` 允许是「消费宿主 context 的组件」；宿主渲染槽时用 `Provider` 注入它才有的能力
   （关菜单、`createNode`、`runExport`、`ctx`…）。**注册表不认识回调的类型**，只保证「条目在不在」。
2. **`host` 是唯一的注入点**：同一 host 的所有条目共享同一份宿主上下文，跨 host 不共享
   （`ExportModal` 的回调不会漏给画布条目）。宿主没提供时退化为空实现（第 2 条的 `NOOP`），
   因此「宿主外渲染」不崩 —— 这也是它可被单测的原因。
   **挂载点命名规则（2026-10-10 补，被单测抓出来的真缺陷）**：**只有页面槽**用 `page.<pageId>`
   前缀（`pageIdOfHost` 按前缀判定，页面槽还要走 `scope: 'page'` 的开关分支）；多级挂载点一律用
   `<域>.<区>`（`studio.slot.tabs` / `canvas.palette` / `header.tools`）。写成 `page.canvas.palette`
   会被误判成页面槽、因 `switchId` 缺失而被静默过滤掉。
3. **布局敏感的宿主由条目自标**：`app`（弹窗 / 浮层，`fixed` / `absolute`）与 `main.tips` 这类宿主，
   槽位**不得加包裹层**；条目把 `markAttrs` 展开到自己的根元素（`shell.tsx` / `ChatHistoryBlock` / `sidebar.footer` 已是此写法）。
   落地形态：`UISlot` 增加「不自标宿主」集合（`APP_HOST` / `MAIN_TIPS_HOST`），并把 8 个弹窗 + 2 个浮层条目的根元素补上自标 —— 这一步即 **M3 的修法**。

### 12.3 不做什么（避免膨胀）

- ❌ 不引入「条目自带任意 props 注入」的通用 DI 容器（那是又一门 DSL）；**每个宿主一个具体 context** 即可。
- ❌ 不让注册表校验回调存在性（注册表只管存在性）；回调缺失 = 空实现 + 该条目不渲染动作按钮。
- ❌ 不为「同 host 多来源」发明优先级表：沿用 `order` + id 稳定排序，冲突按 §11.5 定稿的
  「内置优先 / order 最小者生效 + 告警」处理。
